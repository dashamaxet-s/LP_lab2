# Отчёт: сравнение threading, multiprocessing и asyncio

## Характеристики машины

- **CPU:** Intel(R) Core(TM) i5-10300H CPU @ 2.50GHz
- **Ядер:** 4
- **Логических процессоров:** 8
- **RAM:** 16 ГБ
- **Python:** 3.13.12
- **OS:** Windows 10

## Методика

- **CPU-нагрузка:** подсчёт простых чисел до N = 500000, 4 задачи.
- **I/O-нагрузка:** M HTTP-запросов к мок-серверу с задержкой 0.05 сек.
- **Замер:** `time.perf_counter()`, один прогон.

## Результаты

### CPU-нагрузка (N = 500000, 4 задачи)

| Способ | Время (сек) | Ускорение |
| :--- | :--- | :--- |
| threading | 3.4612 | 1.0x |
| multiprocessing | 1.5218 | 2.27x |
| asyncio | 3.2706 | 1.06x |

### I/O-нагрузка

| Способ | M | Время (сек) |
| :--- | :--- | :--- |
| threading | 50 | 5.3317 |
| multiprocessing | 50 | 5.7852 |
| asyncio | 20 | 1.4769 |

## Объяснение результатов

### Почему threading не ускоряет CPU-нагрузку

GIL (Global Interpreter Lock) — глобальная блокировка интерпретатора CPython. В каждый момент времени байткод Python исполняет только один поток. Чисто вычислительный код не отпускает GIL, поэтому потоки не считают параллельно — они конкурируют за GIL и работают попеременно, добавляя лишь накладные расходы на переключение контекста.

В нашем эксперименте threading показал 3.46 сек — как один поток, а не в 4 раза быстрее.

### Почему multiprocessing выигрывает на CPU

Каждый процесс — это отдельный интерпретатор Python со своей памятью и своим GIL. Процессы не конкурируют за GIL, ОС-планировщик раскидывает их по физическим ядрам. Поэтому CPU-bound задачи масштабируются по числу ядер.

В нашем эксперименте multiprocessing показал 1.52 сек — ускорение в 2.27 раза относительно threading. Не в 4 раза, потому что создание процессов дорого, и не все ядра могут быть задействованы.

### Почему threading и asyncio выигрывают на I/O

GIL освобождается на время блокирующих системных вызовов. Когда поток уходит читать сокет, ждать ответа диска или вызывает time.sleep, он не исполняет байткод Python — он спит внутри ядра ОС. На это время он отпускает GIL, и другой поток может работать.

Asyncio идёт дальше: это кооперативная многозадачность в одной нити. Переключение происходит только на await. Пока один запрос ждёт сеть, цикл ведёт другие. Нет накладных расходов на ОС-потоки, нет конкуренции за GIL.

В нашем эксперименте asyncio при M = 20 показал 1.48 сек — быстрее, чем threading при M = 50 (5.33 сек).

### Почему multiprocessing проигрывает на I/O

Процессы дорогие для I/O: создание + сериализация. I/O-задача не нагружает CPU, поэтому реальный параллелизм по ядрам не нужен. Накладные расходы на процессы не окупаются.

В нашем эксперименте multiprocessing показал 5.79 сек — самый медленный результат.

### Ограничение мок-сервера

Мок-сервер на `http.server` — однопоточный. При M = 50 asyncio создал 50 одновременных соединений, и сервер не справился — часть запросов упала с ошибкой `httpx.ReadError`. Это показывает, что asyncio может создавать очень много соединений, но сервер должен быть готов к этому.

## Выводы

| Нагрузка | Лучший способ | Почему |
| :--- | :--- | :--- |
| CPU-bound | **multiprocessing** | Реальный параллелизм по ядрам (свой GIL у каждого процесса) |
| I/O-bound | **asyncio** | Тысячи соединений в одной нити, без накладных расходов |
| I/O-bound (немного задач) | **threading** | Проще, чем asyncio, и достаточно эффективен |
